# Parity: bootstrap acquisition (server.met / nodes.dat)

Audited **2026-10-02** against the code and the committed fixtures: every row's
status is read from the rmule site it names, and every evidence path exists in
the repository. Schema, status values and the evidence rule:
[README.md](README.md). Cites pin aMule 2.3.3 (`4e8f2b3`).

Direction is from rmule's perspective: `E` = rmule emits/writes, `C` = rmule
consumes/reads/acquires, `B` = both. Cites are SHA permalinks into
`amule-project/amule@4e8f2b3` at the function site.

This surface is **not opcodes** — it is file formats + cold-start acquisition
flows. Rows are wire-visible / on-disk behaviors, traced through the actual
`CamuleApp::OnInit` startup path (`src/amule.cpp`), not just the loaders. The
Kad `KADEMLIA2_BOOTSTRAP_REQ` **wire** row lives in `kad-udp.md`; here the Kad
rows are the **when / from-where** the bootstrap dial is triggered.

**Scope boundary:** reading a user's *pre-existing* aMule config files
(migration import) is out of scope, so those rows are `exempt`. **Acquiring** a
fresh server.met / nodes.dat from a URL is in scope, and a format *parse* the
acquisition path needs is in scope even though the bytes match the on-disk file.

**What runs where.** The core Join Sequence (`rmule-core/src/join.rs`,
[ADR-0067](../../adr/0067-core-owned-startup-join.md)) reproduces amuled's
unattended start: first-run server.met fetch, then both networks in parallel.
`rmule-tools ed2k bootstrap-fetch` runs it, and the cold-start capture below
comes from that run. The `rmule` app does not: nothing in it reaches a server
until the operator connects ([ADR-0095](../../adr/0095-connecting-is-the-operators-act.md)).
The startup rows score the app, and say so where they differ.
