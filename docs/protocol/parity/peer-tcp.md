# Parity: peer TCP

Audited **2026-10-02** against the code and the committed fixtures: every row's
status is read from the rmule site it names, and every evidence path exists in
the repository. Schema, status values and the evidence rule:
[README.md](README.md). Cites pin aMule 2.3.3 (`4e8f2b3`).

Direction is from rmule's perspective: `E` = rmule emits, `C` = rmule consumes,
`B` = both. All aMule cites are SHA permalinks into `amule-project/amule@4e8f2b3`
and point at the handler or sender, not the opcode `#define`.

This is the client↔client **TCP** surface, the largest in the matrix. One socket
is fully **bidirectional**: the same session both pulls parts (Requester
Capability) and serves them (Server Capability), so most transfer opcodes are
`B`. Dispatch is keyed by **`(protocol, opcode)`**: opcode `0x60` is
`OP_ASKSHAREDFILESDIRANS` under `OP_EDONKEYPROT 0xE3` but `OP_QUEUERANKING` under
`OP_EMULEPROT 0xC5`; `0x61` is `OP_ASKSHAREDDENIEDANS` (`0xE3`) vs `OP_FILEDESC`
(`0xC5`); `0x01` is `OP_HELLO` (`0xE3`) vs `OP_EMULEINFO` (`0xC5`). Consume hub:
`CClientTCPSocket::ProcessPacket` (`0xE3`), `ProcessExtPacket` (`0xC5`),
`ProcessED2Kv2Packet` (`0xF4`), dispatched by `PacketReceived`
([ClientTCPSocket.cpp#L1960](https://github.com/amule-project/amule/blob/4e8f2b3c3f90cda23765730546b04c684a92e4f5/src/ClientTCPSocket.cpp#L1960)).
rmule's codecs live in `rmule-peer/src/`, its session in `rmule-peer/src/session/`.

rmule advertises only the extended-protocol features it implements (Honest
Capability Advertisement, [ADR-0047](../../adr/0047-honest-capability-advertisement.md)),
so a compliant peer never picks a path rmule cannot answer.

Opcodes amuled 2.3.3 *defines but never emits or consumes* (or consumes only as a
no-op) are not rows; they are listed under "Defined-but-dead opcodes" at the foot.

#### Hello read surface

What each reader does with the bytes of `OP_HELLO`, `OP_HELLOANSWER`, `OP_EMULEINFO`
and `OP_EMULEINFOANSWER` it receives. Cites are local reference caches, no permalink:
aMule = kno's aMule `ab483654` (`src/`, the Fork Pin; its hello reader is stock
2.3.3's plus the vendor-tag cases), eMule = emule-qt `73fff714` `srchybrid/` (the MFC
eMule it ports). "Throws" means the reader's exception ends the connection
(aMule `ClientTCPSocket.cpp:249`, eMule `ListenSocket.cpp:1791-1850`). A rule where
rmule is stricter than both references is a defect. Bench leg: `ipv6-dialect
peer-hello-surface` (`tools/interop-harness`), run `1790611695`, `OBSERVED` 32 of 35: each
bench client's own `OP_HELLO` (fixtures `client_software/captured/hello-surface-op-hello-20260928/`)
and `OP_HELLOANSWER` read strictly, and every client's reaction to rmule's hello ending in
`CT_MOD_VERSION` = `rmule 0.1.0` — Secure User Identification, a part each way, no
`OP_EMULEINFO`, the link held. No bench client is older than eMule 0.42, so no legacy
`OP_EMULEINFO` reached rmule: every legacy row stays derived.

**Still refused, and why.** A tag type byte no client defines (its width is unknowable,
so is every later offset); a tag, string, `BLOB` or field running past the frame (a
length is never believed beyond the bytes present); a hash-size byte other than 16 (the
answer has no size field to echo). The declared tag count sizes no reservation, and a
frame is at most 16 MiB (`rmule_primitives::packet`), so accepting more never means
allocating on a peer's word.
