# Parity: peer UDP (extended eMule)

Audited **2026-10-02** against the code and the committed fixtures: every row's
status is read from the rmule site it names, and every evidence path exists in
the repository. Schema, status values and the evidence rule:
[README.md](README.md). Cites pin aMule 2.3.3 (`4e8f2b3`).

Direction is from rmule's perspective: `E` = rmule emits, `C` = rmule consumes,
`B` = both. All aMule cites are SHA permalinks into `amule-project/amule@4e8f2b3`
and point at the handler or sender, not the opcode `#define`.

This is the client↔client **UDP** surface: eMule's extended-protocol datagrams
(`OP_EMULEPROT 0xC5`) that ride the *shared* client UDP socket
(`CClientUDPSocket` / `theApp->clientudp`) — the same socket that carries all of
Kad (`0xE4`/`0xE5`). It is a source-reask fast path: a queued downloader refreshes
its queue position and the source's part availability over a single datagram
instead of re-establishing a TCP session (peer-tcp.md), plus two firewall-callback
mechanisms. Every opcode here is consumed *and* emitted by aMule, so all rows are
`B` from a full-citizen perspective.

rmule binds one client-UDP socket (`rmule-net/src/ed2k/client_udp.rs`) that
carries the reask surface and the Kad node on the same port, demuxed by
`rmule-core/src/client_udp/engine.rs`. The UDP opcodes live in
`rmule-peer/src/reask.rs` (`ClientUdpOpcode`), apart from the TCP-only
`PeerOpcode`.

Opcodes amuled 2.3.3 *defines but never emits or consumes* are not rows; they are
listed under "Defined-but-dead opcodes" at the foot of this file.
