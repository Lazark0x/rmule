# rmule interop harness

`rmule-interop-harness` is an opt-in local interoperability runner for proving rmule against external eMule-compatible processes.

The first flow is:

```bash
cargo run -p rmule-interop-harness -- \
  amule-serves-rmule-downloads \
  --build-images \
  --timeout 300
```

The flow creates a retained run directory under `.scratch/interop-runs/`, generates a deterministic `synthetic/shared.bin`, hashes it into `synthetic/shared.ed2k.txt`, starts a real eD2k server container, starts an aMule/amuled container, waits for readiness, runs `rmule-tools ed2k download start`, and compares `rmule/output.bin` byte-for-byte with the synthetic source file.

## Wire smoke (`bench-smoke`)

```bash
cargo run -p rmule-interop-harness -- \
  bench-smoke \
  --skip-build \
  --timeout 600
```

Starts `rmule/interop-eserver:local`, waits ready, then runs
`rmule-tools ed2k server probe` **inside the interop network** (reaching the
server's UDP ports by container name, so no host NAT drops the reply) and
distils two decision inputs into `bench-smoke-summary.toml` and prominent
stdout lines:

- **`compression_advert`** — from the IDCHANGE `SRV_TCPFLG` word (bit `0x01`).
  Requires a completed login; the probe binds a High-ID back-connect
  listener so the eserver does not assign a Low ID.
- **`crypt_advert`** — from the `0x97` `SRV_UDPFLG` word (`0x200`
  `UDPOBFUSCATION`), read via a plain `0x96` status ping (TCP+4) and the raw
  obfuscated crypt-ping (TCP+12). This is the check that
  resolves whether an obfuscation-capable eNode is ever needed.

The probe captures **no counterparty fixture** — it reports wire facts only.

`--udp-ports-advert <port>` rides `CT_EMULE_UDPPORTS` (`0xF9`, ADR-0091) on the
probe's login — the fifth tag a running core sends whenever its client-UDP
socket is bound — and the summary's `login_accepted` / `udp_ports_advert` say
whether this server body still takes the login. Run it beside a bare control:
the claim is that the flag words and the ID class do not move.

`--advertise-ipv6 <addr>` adds `CT_MOD_IP_V6` (`0xAE`) with its `SRVCAP_IPV6`
bit (ADR-0087). Beside `--udp-ports-advert` the login carries **six tags**
(`…,0xFB,0xAE,0xF9`), the login a dual-stack core sends (ADR-0047, ADR-0091).
The summary's `login_tags` and `advertised_ipv6` name what the login carried;
`login_accepted` and the flag words are Lugdunum's answer. **Lugdunum takes
the six-tag login unchanged** (measured 2026-10-18, harness `d02dd2d5`,
`rmule/interop-eserver:local`): `bench-smoke --udp-ports-advert 4672
--advertise-ipv6 2001:db8::9`, run `1792360674`, read `login_tags` 6,
`advertised_ipv6` `2001:db8::9`, `udp_ports_advert` `0x00001240` and
`login_accepted` true with a High ID (the probe's own address), `SRV_TCPFLG`
`0x000017F9`, `SRV_UDPFLG` `0x000017FB`. The bare control, run `1792359978`
(4 tags), and the five-tag run `1792360532` read the same ID class and the
same two words. An earlier six-tag run, `1792360183`, read the same login
answer and words, but its plain `0x96` status pings (TCP+4 and TCP+0) went
unanswered while its crypt ping was answered; the repeat answered both, and
the silence did not recur.

## Low-ID Callback (ADR-0039)

```bash
cargo run -p rmule-interop-harness -- \
  amule-low-id-callback \
  --build-images \
  --timeout 420
```

The same shape as `amule-serves-rmule-downloads`, with two differences: the aMule
sharer is forced to **Low-ID** (`AMULE_FORCE_LOW_ID=1` + `--cap-add NET_ADMIN`; its
entrypoint drops inbound TCP so the server cannot reach it back), and rmule runs
`ed2k download start --serve` so it binds the inbound listener — making it High-ID
and **callback-capable**.

**Run-or-exempt disposition (ADR-0040).** This is a *compatibility-tier*
flow and does not byte-complete. Byte-tracing shows the Lugdunum test
eserver (17.15) never surfaces the connected Low-ID aMule as a source: rmule sends a
byte-correct `OP_GETSOURCES` and the server returns no `OP_FOUNDSOURCES` — even with
the file indexed (`file_count = 2`) — so rmule correctly discovers no candidate and
never emits an `OP_CALLBACKREQUEST`. That is the documented Lugdunum Low-ID
limitation (ADR-0040), not a rmule fault: the eserver is a closed, emulated binary
that mishandles the multi-client Low-ID topology, so the design is to work *around*
it. The flow therefore asserts the honest observable — rmule's own **callback
capability** against the real server while a real Low-ID aMule shares the file: it
binds its inbound listener (`serving_started`) and the server's High-ID reachability
probe reaches that listener (the wire proof rmule is dialable, hence High-ID). The
run is bounded (`--max-seconds`) and the verdict lands in
`amule-low-id-callback-verdict.toml` (`callback_capable = true`). The byte-completing
adopt path — request-callback → dial-back → adopt → verified part — is proven
deterministically in the in-process **correctness tier**
(`crates/rmule-core/tests/callback_loopback.rs`, ADR-0040); the callback wire itself
is pinned from aMule source in `docs/reference/notes/low-id-callback.md`.

## Private Kad Source-Lookup Capture

`kad-source-lookup-capture` runs a **private** aMule-to-aMule Kad topology and a
passive packet-capture sidecar to gather source-lookup evidence. rmule does not
participate; there is no eD2k server.

```bash
cargo run -p rmule-interop-harness -- \
  kad-source-lookup-capture \
  --build-images \
  --timeout 300
```

- **Private-only rule:** no public Kad bootstrap URLs, no imported public
  `nodes.dat`, no external Kad peers. The only bootstrap input is a
  harness-generated private `nodes.dat`.
- **Phase 1 (default):** publisher + requester. Targets a High ID source-result
  fixture.
- **Phase 2 (opt-in):** add `--routing-nodes 3` for at least five private nodes
  and routing-order evidence.
- The full `capture/kad/kad.pcap` stays under `.scratch/interop-runs/` and is
  never committed; only manually promoted minimal datagrams are checked in.

**Forming a real private mesh.** This RFC1918 + patched-image recipe
(`FilterLanIPs=0`, LAN mode) is retained for the existing source-lookup capture
but is **retired from evidence duty**: LAN mode falsifies aMule's
firewall self-check and publish-tolerance zone. The evidence path is now the
**fake-public swarm on stock aMule** (Config A, below).

## Fake-public Kad swarm (Config A)

Stock aMule 2.3.3 hard-blocks an all-RFC1918 Kad routing table — every
contact-admission path funnels through `IsGoodIPPort`, whose LAN filter is
hardcoded on. The answer (the Config-A finding) is to address the swarm from the **RFC 5737 documentation ranges**
(`203.0.113.0/24`, `198.51.100.0/24`, `192.0.2.0/24`), which aMule does *not*
classify as LAN — so the node accepts them on its **normal, non-LAN-mode**
paths and every captured wire is genuine. The network is **`internal`** so an
isolated swarm never emits a Kad datagram to the real internet. The harness
owns the address plan (`fake_public.rs`: `--internal` bridge + deterministic
static `--ip`s, `.2` up, capped per `/24`), never Docker's defaults.

### Stock aMule Kad smoke (`kad-smoke`)

```bash
cargo run -p rmule-interop-harness -- \
  kad-smoke \
  --skip-build \
  --connect-deadline 420
```

Two **stock** aMule nodes (seed + joiner) on one fake-public `/24`; the joiner
bootstraps to the seed via a seed `nodes.dat`. Success = at least one reports
`Kad: Connected` (either `(ok)` or `(firewalled)`), polled via `amulecmd
Status` with bounded retries. The cold-boot window is ~3–6 min;
a non-connect within `--connect-deadline` is a **major finding** (it
would falsify the Config-A verdict) — diagnostics are retained, nothing forced.

Known runtime note: the capture sidecar (source-lookup flow) needs
`NET_RAW`/`NET_ADMIN`; Docker is the verified runtime.

## rmule-tools SUI key

Every `rmule-tools` node proves its hellos with Secure User Identification
(ADR-0041). Its User Hash is the `--user-hash` the flow pins, fixed when the
Core is built; the SUI key comes from the node's store. An in-memory store
mints a new key every run, and an aMule that keeps `clients.met` between runs
binds the pinned hash to the first key it saw, so the next run's proof is a
hash/key mismatch. The commands that flatten the shared identity
operands (`download start`/`resume`, `search`, `serve`, `nat portmap`) take
`--identity-dir <DIR>`: the key for a hash lives in `<DIR>/<HASH>`, created on first use and
reused after. A download without it uses its `--data-dir` store, which is
already persistent. A flow that reuses an aMule's `clients.met` across
runs and pins an rmule hash passes the same `--identity-dir` to every run.

**SUI V2 has no stock-aMule leg.** The V2 challenge IP (which address a signature
binds) is proven by the golden-input tests in `rmule-peer`
(`peer_secure_ident`), not on the bench: stock aMule advertises SecIdent nibble 3
(`BaseClient.cpp:1088`) and signs V1 for any peer whose nibble has bit 1 set
(`BaseClient.cpp:2089`), and rmule signs V2 only toward a peer advertising
exactly 2, which no stock client does. A bench run with Kad open therefore shows
V1 in both directions; `amule-direct-sui` stays the V1 regression.
`AMULE_FRESH_IDENTITY=1` wipes `clients.met` instead, so either one keeps the
proof valid.

## Bench variant env

aMule containers are driven by `entrypoint.sh` env vars (pass extras with
`--amule-env KEY=VALUE`). Beyond the crypt knobs (`AMULE_CRYPT_SUPPORTED` /
`_REQUESTED` / `_REQUIRED`) and Low-ID (`AMULE_FORCE_LOW_ID=1` + `--cap-add
NET_ADMIN`):

| Env | Effect |
|---|---|
| `AMULE_FRESH_IDENTITY=1` | Wipe `preferences.dat` / `cryptkey.dat` / `preferencesKad.dat` / `clients.met` / `known.met` on start — a fresh eD2k + Kad identity and zeroed credit/recheck state. |
| `AMULE_KAD_FILTER_LAN_IPS` | `FilterLanIPs` value in `kad-node` mode. Default `0` (patched LAN-mesh scenarios). The stock fake-public swarm sets `1` (Config A: stay out of LAN mode). |
| `AMULE_DOWNLOAD_NO_WAIT` | Download-hold mode (flow I): after `Add`ing `AMULE_DOWNLOAD_LINK`, settle (`AMULE_DOWNLOAD_SETTLE`, default 25 s) so the source list fills from get-sources and the sources *establish*, report `rmule-amule-download-sources-ready`, then idle instead of polling for a completed file — the aMule stays a downloader holding its learned sources for the capture dial. The window is bounded on both sides: too short and the sources are not yet established (aMule exchanges only `DS_DOWNLOADING`/`DS_ONQUEUE` sources), too long and the file completes, at which point it is no longer a partfile and has no source list to answer with. |
| `AMULE_DEFAULT_ROUTE_VIA` / `_VIA6` | Point the container's default route at a **NAT Gateway** (ADR-0092). A client on the gateway's LAN bridge has no egress of its own — the bridge is created with `enable_ip_masquerade=false` — so this is what puts it behind the NAT. A route is a *network condition*, the same legal knob class as `AMULE_FORCE_LOW_ID`'s inbound DROP, and changes nothing about how the client speaks the protocol. The same pair exists as `EMULEQT_DEFAULT_ROUTE_VIA` and `RMULE_DEFAULT_ROUTE_VIA` on the emule-qt and rmule images. |
| `AMULE_QUEUE_SIZE_PREF` | `QueueSizePref` value (aMule's upload queue is `pref × 100` slots). `0` is the hand-driven `0x93` capture recipe: `ClientUDPSocket.cpp` answers an UNKNOWN sender's reask for a **shared** file with `OP_QUEUEFULL` iff `(waiting + 50) > GetQueueSize()`, so a zero pref makes the near-full branch unconditional on a quiet bench — a legal user preference, not a patch (ADR-0045). Drive it with `rmule-tools ed2k peer reask-capture <ip:udp> --shared-hash <hash>`. Unset leaves aMule's default (`50` → 5000). |
| `AMULE_SLOT_ALLOCATION` | `SlotAllocation` value (KB/s per upload slot). With a capped `AMULE_MAX_UPLOAD` aMule keeps `round(MaxUpload / SlotAllocation)` slots, never fewer than `MIN_UP_CLIENTS_ALLOWED` = 2 (`UploadQueue.cpp:297-320`), so `AMULE_MAX_UPLOAD=400` with `AMULE_SLOT_ALLOCATION=200` gives a fast uploader exactly two slots, and its 10 MB session kick (`UploadQueue.cpp:576-583`, `OP_OUTOFPARTREQS` then `OP_QUEUERANKING`) lands about a minute into a grant once someone waits. A legal user preference. Unset leaves aMule's default (`2`). |
| `RMULE_FORCE_LOW_ID_TCP_PORT` (`rmule-tools` image) | `AMULE_FORCE_LOW_ID`'s twin for rmule: the entrypoint drops inbound TCP to that listener port (connections rmule opens itself still run), so the server's High-ID probe fails and rmule logs in Low ID. Needs `--cap-add NET_ADMIN`. Used by `server-callback-serve`. |

The **golden-author flush** (`server.met` + `nodes.dat`) is a library helper,
`flow::flush_golden_files` (`amulecmd Shutdown` → `docker cp` out to the
run dir), for the goldens the acceptance flows author — provenance-tracked, never
auto-promoted.

## Bench acceptance tests (`RMULE_BENCH=1`)

The end-to-end acceptance flows live in
[`tests/harness/acceptance.rs`](tests/harness/acceptance.rs) as thin `#[test]`
wrappers that each drive a flow through its CLI subcommand and assert the run-dir
artifacts. Every wrapper is `#[ignore]` **and** skips (printing a message)
unless `RMULE_BENCH=1`, so a plain `cargo test` never touches Docker. Run the
whole suite serially:

```bash
RMULE_BENCH=1 cargo test -p rmule-interop-harness --test harness \
  -- --ignored --test-threads=1 acceptance::
```

A wrapper passes every path the flow reads **absolutely**, build contexts and
bind-mounted files alike: the subcommand defaults are repo-root-relative and
`cargo test` runs from this package's root, so a default left in place resolves
one directory too deep. The coordinator's `config.toml` is the one that bites
under `--skip-build` — it is mounted, not built, so it is read either way.

The wrappers hold no orchestration logic — the flows stay library functions
(`flow::run_*`) behind the subcommands below, which remain the surface for
individual/debug runs and hand-driven captures.

`RMULE_BENCH_VERDICT_DIR` re-scores a retained run against the markers the
harness reads today: the record codes rmule-tools prints (`serve.serving_started`,
`download.peer_selected`, `server.connected`, ...). A run saved before the flows
read those codes holds the older event-line text, so a flow that gates on a
marker finds it absent and scores the run as a failure. The scorer has no
fallback to the old text; re-score such a run with a harness built from before
the change, or drive the flow again.

flow (`late-port-test`, `1791413152`), the Core-pumped Kad buddy flow with its three aMule-requester

## Image Recipes

Checked-in recipes live under `tools/interop-harness/images/`.

The NAT and IPv6 waves add four (ADR-0092):

- **`natgw`** — the **NAT Gateway**. debian-trixie + nftables + conntrack, one
  container per client, translating with a declared `NAT_TYPE`
  (`port-restricted` | `restricted` | `full-cone-pinned` | `symmetric`).
  `full-cone-pinned` is named for what it is: stateful NAT cannot express a
  general endpoint-independent filter, so it is a full cone *for the one pinned
  UDP port* and a flow may not claim more. Address-Dependent Mapping ("hard"
  NAT) is absent because netfilter cannot key a mapping on the destination
  address alone. Needs `--cap-add NET_ADMIN` and three sysctls, one of which is
  not tuning: `net.netfilter.nf_conntrack_udp_timeout=180`, because the Linux
  default of 30 s violates RFC 4787 REQ-5's two-minute floor by 4× and would
  close a punch window before the punch. `natgw-proof` dumps the ruleset, the
  dynamic set and the conntrack table into the run dir — taken by `docker exec`,
  not by a shutdown trap, since teardown is `rm -f` and runs no trap. Rebuilt on
  every `natgw-selfproof`/`natt`/`portmap` run regardless of `--build-images`,
  like `rmule-tools`: it is a 30 s Debian layer plus two `COPY`s, so
  a wrapper that already passes `--skip-build` still measures an edited
  `entrypoint.sh`/`natgw-proof.sh`, never a stale cached image. Measured on
  colima/Docker 29.2.1: an unchanged rebuild is Docker-cache-free, ~0.06-0.2 s.
- **`natprobe`** — the **Reflector Probe**'s server half: two fake-public
  addresses (the second added with `ip addr add` under `NET_ADMIN`, so both stay
  in the `/24` the counterparties already accept) × two UDP ports, answering one
  ASCII line from whichever socket the request asks for. Not a STUN server: RFC
  5780's *procedure* is reused, its wire format is not. **Stimulus, never
  evidence.** Rebuilt unconditionally too, same reason and same measured cost as
  `natgw` — every flow that runs it (`natgw-selfproof`, `natt`, `portmap`)
  needs no `--build-images` to see an edited recipe.
- **`miniupnpd`** — the **Port-Mapping Gateway** for the port-mapping flows: alpine-edge +
  `miniupnpd-nftables=2.3.10-r0`, pinned by exact package version because
  `edge` moves. It is both the NAT (a plain port-preserving SNAT — the same
  recipe `natgw`'s `port-restricted` branch renders, so the flows claim a NAT
  type `natgw-selfproof` already proved) and the router rmule's **Port Mapper** talks to,
  answering UPnP-IGD2, NAT-PMP and PCP. The nftables flavour, not the iptables
  one, for the same reason `natgw` carries no iptables: `nft list ruleset` is
  the NAT Type Proof and forwarding that lived half in another front-end would
  make that dump incomplete. Its own startup banner reports the build
  (`ipv6 NAT-PMP PCP leasefile igdv2`) and the entrypoint writes both lease
  tables into the run dir, so a flow reads what the daemon wrote rather than
  what the harness asked for. Two measured constraints live in its README: the
  WAN cannot be an RFC 5737 documentation prefix (miniupnpd refuses those as an
  external IP), and the two sides are resolved from their **addresses** rather
  than from an `eth0`/`eth1` assumption, because Docker does not promise a
  stable interface order and a gateway that resolves `listening_ip` to its
  public side refuses to start at all.
- **`amule-kno`** — kno's aMule at a **Fork Pin** (owner `kno`, branch
  `integration/network-parity`, commit `ab483654`, upstream base
  `amule-org/amule` `1cbc7c50`), the only body carrying IPv6 activation, Kad
  `0x0a`, uTP and the eMuleAI NAT-T rendezvous at once. Derived from the fork's
  own Dockerfile with the from-source ffprobe stage stripped and the s6
  operational layer replaced by a harness entrypoint; every *build* flag stays
  the fork's, including the `ENABLE_QUIC` arg `build.sh --quic` selects. The pin
  is verified against the reference clone before the build and lands on the
  image as `org.rmule.amule_kno.*` labels; `build.sh --runtime-only` reuses an
  already-built compile-stage image and skips recompiling, and `AMULE_KNO_SRC`
  (a pinned clone elsewhere on the host) is the pin check's fallback
  when a worktree carries no in-tree vendored source.
  `--build-images` builds it only through `build.sh` (the `--quic` variant when
  the image tag ends in `:quic`), which makes the compile stage too, so a cold
  host no longer fails on a missing `amule-kno-build` image; a missing reference
  clone fails with the script's own message. Every flow that starts the image
  checks its `org.rmule.amule_kno.commit` (and `.quic`) label first and refuses
  an off-pin image unless `RMULE_BENCH_AMULE_KNO_OFF_PIN=1`, and the verdict
  body's `pin` is read off that label, not written as a constant.
- **`emuleqt`** — emule-qt's headless `emulecored` (ADR-0082) at the commit in
  `docs/reference/emule-qt/emule-qt.meta.toml`. `--build-images` builds it only

**Bench-image hygiene.** The `rmule-tools` driver image is a thin runtime
around the binary the warm host-cached prebuild produced
(`.scratch/interop-target-cache`, the cache the Kad flows run from): the
harness stages that binary, the recipe's `Dockerfile` and its entrypoint in
`.scratch/interop-rmule-tools-context` and builds from there, so an unchanged
tree is an unchanged `COPY` and rebuilds nothing. Every NAT or IPv6 flow builds
the Bench Doctor's own image (`natgw`, or `miniupnpd` for `portmap`) first, runs
the doctor, and writes a skip before it builds anything else. The remaining
rust-toolchain multi-stage recipes
(`rmule-node`, `amule-kad-patched`) build under colima's legacy
`docker build` — no BuildKit, so every stage commits as its own image and
only the final one gets `-t`. Each such `AS build` stage carries
`org.rmule.bench.stage=1`; `main()` runs a label- and dangling-scoped
`docker image prune` after every harness subcommand
(`Docker::prune_bench_stage_images`), so the ~3 GB non-final stage never
outlives the run that produced it. Every final image (these two, `rmule-tools` plus
`amule`/`amule-debug`) carries `org.rmule.bench=1` instead, which scopes
the cleanup of the OTHER accumulation: tagged bench images
(`rmule/interop-rmule-tools:<tag>`, `rmule/interop-amule-debug:<tag>`) that
nobody removes. `docker images --filter label=org.rmule.bench=1` lists them and
`docker rmi` removes the ones no longer wanted. Neither label ever matches an
image this harness did not build.

`bench-doctor` runs before any NAT or IPv6 flow and measures what the runtime
can actually do — nftables dynamic sets, conntrack, whether `--sysctl` really
raised the conntrack UDP timeout, bridge netfiltering, an `ip6` NAT chain, and
whether the daemon will build an `--ipv6` bridge. A flow that asks for a
capability it did not get **skips with the probe output that said so**; nothing
here can turn an unmeasured capability into a pass. A host whose VM rebooted
loses `br_netfilter` (`bridge-nf-call-iptables=unreadable`) and every NAT flow
`SKIPPED`; `sudo modprobe br_netfilter` in the VM restores it.

**Run-dir mounts need a host path the container runtime can see.** On
colima the VM mounts `$HOME` and nothing else, so a `--run-root` under
`/tmp` (or a worktree there) leaves every bind mount pointing at a directory
inside the VM and the run dir comes back empty. Pass `--run-root` under the
home directory when the checkout is not.

The repository may commit Dockerfiles, entrypoints, configuration templates, pinned external URLs/checksums, and build instructions. It must not commit downloaded eD2k server binaries, aMule source archives, built binaries, generated image layers, or run artifacts.

## Run Artifacts

Each run writes:

```text
.scratch/interop-runs/<timestamp>/
  resolved-config.toml
  run.toml
  synthetic/shared.bin
  synthetic/shared.ed2k.txt
  rmule/rmule.redb
  rmule/output.bin
  rmule/stdout.log
  rmule/stderr.log
  logs/server/stdout.log
  logs/server/stderr.log
  logs/amule/stdout.log
  logs/amule/stderr.log
  docker/network-id.txt
  docker/server-container-id.txt
  docker/amule-container-id.txt
```

`resolved-config.toml` holds the flow's options. `run.toml` is the run record the
harness writes itself, whether the flow passed or not: `started_unix_ms`,
`harness_commit` (`git rev-parse HEAD` of the workspace the harness was built
from), `dirty` and `dirty_paths` (a count, not the paths), `rmule_binary_sha256`
of the prebuilt `rmule-tools` under test and `rmule_image_id` of the driver
image, `counterparty_images` (image tag to image id for every image the run
started), and at the end `finished_unix_ms`, `duration_ms` and `outcome`
(`pass`, `fail`, `skip` or `error`: an error returned by the flow, a `FAIL` or
all-`SKIPPED` set of verdict files, otherwise `pass`). Tags alone do not tell two
builds apart, so a repeat of a flow with the same options is redundant only when
the commit, `dirty` and the binary hash or image id all match. Verdict bodies
name rmule as `<commit>[+dirty] sha256 <prefix>` from the same record. A re-score
of a retained run never rewrites the record; it appends one `rescored_at` line.

Use `--keep-containers` to leave the containers and network running. The harness prints retained container and network names in that mode.
